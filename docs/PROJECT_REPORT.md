# Moodium — звіт про виконану роботу

**Тема:** «Трекер настрою з індексом вигорання»
**Дисципліна:** крос-платформне програмування
**Стек:** React Native 0.86 + Expo SDK 57, TypeScript (strict), Expo Router, SQLite (локально) + Supabase (акаунт і хмарна синхронізація)

Moodium — застосунок для щоденних записів про настрій, який рахує **індекс вигорання (0–100)** *на пристрої* (аналіз не залежить від сервера), пояснює його, прогнозує динаміку й дає конкретні поради. Працює на iOS, Android (Expo Go) і у вебі (ноутбук). Записи синхронізуються між пристроями через акаунт (Supabase), тож телефон і браузер показують один і той самий щоденник.

---

## Етап 1. Проєкт і база даних

**Що зроблено**
- Проєкт Expo з файловою навігацією (Expo Router, вкладки), TypeScript у режимі `strict`.
- Локальна БД SQLite (`expo-sqlite`), нормалізована схема з 5 таблиць: `entries`, `factors`, `tags`, `entry_factors`, `entry_tags` (зв'язки «багато-до-багатьох», каскадне видалення).
- **Міграції схеми** через `PRAGMA user_version`: v1 — початкова схема, v2 — нові поля (`sleep_hours`, `stress`, `workload`) і таблиця `settings`. Старі записи при оновленні зберігаються (міграцію перевірено на копії v1-бази).
- Запити в одному модулі (`database/queries.ts`): транзакції, upsert «один запис на день».

**Чому так:** local-first — застосунок читає й пише в локальну SQLite, тому працює без інтернету й швидко; хмарна копія (етап 6) лише синхронізується з нею.
**Де в коді:** `database/schema.ts`, `database/queries.ts`, `database/types.ts`.

## Етап 2. Щоденний запис (CRUD)

**Що зроблено** — екран *Today*:
- настрій (5 рівнів, SVG-обличчя), інтенсивність 1–10;
- **сон (години), стрес і навантаження (1–5)** — дані, потрібні для індексу вигорання;
- фактори дня (робота, сон, спорт, спілкування), нотатка, теги;
- створення, оновлення, видалення запису; перехід на **будь-який минулий день** (можна заповнити пропущене).

**Де:** `app/(tabs)/index.tsx`, `components/MoodPicker.tsx`, `ScalePicker.tsx`, `Stepper.tsx`, `FactorPicker.tsx`, `TagInput.tsx`.

## Етап 3. Історія та візуалізація

**Що зроблено** — екран *History*:
- календар-теплокарта місяця (колір дня = настрій);
- лінійний графік настрою (`react-native-chart-kit`);
- пошук по нотатках, фільтр за настроєм; клік по запису відкриває його для редагування.

**Де:** `app/(tabs)/history.tsx`, `components/MoodCalendar.tsx`, `MoodTrendChart.tsx`, `EntryCard.tsx`.

## Етап 4. Головна функція — індекс вигорання

Це ядро роботи. Уся логіка — **чисті функції без залежності від React**, тому її можна тестувати окремо.

| Частина | Що робить | Файл |
|---|---|---|
| Аналіз тексту | Словникова тональність нотаток (українська + англійська), враховує заперечення («не втомився» → позитив) | `utils/sentiment.ts` |
| Індекс | Зважена сума **8 сигналів** за 14 днів. Сигнал без даних пропускається, ваги перераховуються | `utils/burnout.ts` |
| Пояснення | Для кожного сигналу: що виміряно словами, статус, **скільки балів додає** (сума = індекс) | `utils/describe.ts` |
| Поради | Конкретні кроки з числами користувача («лягайте на 45 хв раніше») | `utils/advice.ts` |
| Прогноз | Лінійна регресія індексу → «через N днів зона високого ризику» | `utils/forecast.ts` |
| Тиждень | Підсумок 7 днів проти попередніх 7 | `utils/recap.ts` |
| Кореляції | Вплив факторів на настрій (з/без), статистика тегів, кореляція Пірсона «сон ↔ настрій» | `utils/insights.ts` |

**Вісім сигналів і ваги:** рівень настрою 22%, тональність нотаток 15%, динаміка настрою 13%, сон 13%, дні з поганим настроєм 10%, стрес і навантаження 10%, серія перевантажень 10%, відновлення 7%.
**Рівні ризику:** < 35 низький, 35–59 помірний, ≥ 60 високий.

**Чому не нейромережа:** результат має бути *пояснюваним* — користувач бачить, чому саме такий індекс. Для невеликого особистого набору даних це й надійніше.

## Етап 5. Нативні можливості та крос-платформність

| Можливість | Бібліотека | Що дає |
|---|---|---|
| Сповіщення | `expo-notifications` | щоденне нагадування; попередження про високий ризик і про прогноз «через ≤3 дні» |
| Біометрія | `expo-local-authentication` | блокування щоденника Face ID / відбитком |
| Файли | `expo-file-system`, `expo-sharing`, `expo-document-picker` | експорт JSON/CSV, імпорт JSON з валідацією |
| PDF-звіт | `expo-print` | документ для користувача чи психолога |
| Хаптик | `expo-haptics` | тактильний відгук |
| Акаунт і синхронізація | `@supabase/supabase-js` | вхід, спільний щоденник на всіх пристроях (етап 6) |

**Адаптивність (телефон → планшет → ноутбук):**
- Інтерфейс у стилі *bento*: плитки на сітці, яка сама визначає 1, 2 або 3 колонки за шириною контейнера (`components/Bento.tsx`).
- На широких екранах нижня панель вкладок стає **бічною**, вміст центрується.
- Власний набір SVG-іконок (`components/Icon.tsx`) — однаковий на всіх платформах, без емодзі.
- Тема **світла / темна / авто**, дві мови (**українська / англійська**), іконка й splash з логотипу.

**Особливості веб-версії (ноутбук)** — там, де API телефона недоступні, застосунок підміняє їх браузерними:
- **PDF-звіт:** `expo-print` у вебі друкує всю сторінку, тому звіт відкривається в прихованому `iframe` і друкується окремо («Зберегти як PDF» у діалозі браузера).
- **Експорт JSON/CSV** — звичайне завантаження файлу; **імпорт** читає файл із вибору браузера.
- **Сповіщення** — Notification API браузера; працюють, поки вкладка відкрита (фоновий push без сервера неможливий). Є кнопка «Тестове сповіщення».
- **Діалоги** `Alert.alert` у `react-native-web` порожні, тому замінені на `window.alert/confirm` (`services/webAlert.ts`).
- **Біометрія** у браузері недоступна, тому блок «Приватність» там прихований.
- Застосунок можна встановити як PWA (`public/manifest.json`).

## Етап 6. Акаунт і хмарна синхронізація

**Що зроблено**
- **Вхід і реєстрація** (email + пароль, Supabase Auth): окрема форма реєстрації з іменем і підтвердженням пароля, сторінка «Підтвердьте email», ім'я змінюється в Налаштуваннях. Застосунок відкривається лише після входу (якщо в збірці задані ключі Supabase; без них працює локально, як раніше).
- **Пароль:** для нових паролів діють правила — щонайменше 8 символів, літери й хоча б одна велика (`utils/password.ts`). Зміна пароля в Налаштуваннях відкриває вікно, де потрібно ввести поточний пароль, новий і повтор нового; поточний пароль перевіряється перед зміною.
- **Відновлення пароля:** «Забули пароль?» надсилає на пошту одноразовий код (Supabase `resetPasswordForEmail` + `verifyOtp`); користувач вводить код у полі з окремими клітинками на кожну цифру (перевірка відбувається автоматично після останньої цифри), і лише потім задає новий пароль. Код, а не посилання, обрано, бо він однаково працює на телефоні й у браузері. На час відновлення застосунок не пускає всередину, доки новий пароль не збережено.
- **Гібридна модель даних:** SQLite лишається повною локальною копією на кожному пристрої (працює без мережі), а Supabase Postgres — спільна копія. Синхронізація двостороння: після входу, при поверненні в застосунок і через ~1,5 с після кожного збереження чи видалення запису.
- **Розв'язання конфліктів:** «остання зміна перемагає» для кожного дня; видалення синхронізуються через «надгробки» (таблиця `tombstones`, міграція схеми v3). Алгоритм злиття — чиста функція `utils/syncPlan.ts` з окремими тестами.
- **Вихід з акаунта:** спершу вивантажуються незбережені зміни, потім локальна копія очищається, щоб наступний користувач того самого пристрою не побачив чужого щоденника.

**Безпека**
- У таблиці `entries` увімкнено **Row Level Security**: користувач бачить і змінює лише рядки зі своїм `user_id` (`supabase/schema.sql`).
- У застосунку використовується лише *publishable* ключ; secret-ключ ніде не потрібен. Ключі лежать у `.env` (не потрапляє в git).

**Де в коді:** `services/supabase.ts`, `services/sync.ts`, `context/Sync.tsx`, `utils/syncPlan.ts`, `components/AuthGate.tsx`, `AuthForm.tsx`, `ConfirmEmail.tsx`, `AccountTile.tsx`, `supabase/schema.sql`.

**Компроміс щодо приватності.** Після входу записи й нотатки зберігаються на сервері Supabase, прив'язані до акаунта (раніше все було лише на пристрої). Це свідомий вибір заради синхронізації між телефоном і ноутбуком; сам аналіз і розрахунок індексу, як і раніше, відбуваються локально.

## Етап 7. Якість і перевірка

- **82 автоматичні тести** (16 наборів, Jest): сентимент, індекс, поради, прогноз, підсумок тижня, експорт/імпорт, PDF-звіт, дати, переклади, алгоритм синхронізації. Серед них перевірки, що *бали сигналів у сумі дорівнюють індексу* і що обидві мови мають однакові ключі.
- Перевірка типів `tsc --noEmit` без помилок.
- Збірка бандлів для iOS і Android проходить; веб-версію перевірено в Chrome на розмірах 390–1440 px у світлій і темній темах.
- Знайдені й виправлені в ході перевірки помилки: порожній графік у вебі, невидима активна вкладка бічної панелі, дублі на осі графіка, регістр дат українською, збій при відкритті бази у двох вкладках.

## Як показати на захисті

1. Налаштувати `.env` і Supabase (див. README), запустити `npx expo start`, відкрити в Expo Go і зареєструватися (або увійти).
2. **Settings → Демо-дані** — заповнює 30 днів: спокійний початок і спад до вигорання.
3. **Insights** — індекс 70 («високий ризик»), причини, кроки, прогноз, розбивка за сигналами. Натиснути «Як рахується індекс?».
4. Перемкнути тему й мову в Settings; відкрити на ноутбуці (`w` у терміналі) — бічна панель і 3 колонки.
5. **Поділитися PDF-звітом.** Запустити `npm test`.

## Можливі запитання викладача

- **Чому ваги саме такі?** Це експертне припущення на основі відомих чинників вигорання (сон, навантаження, настрій, відновлення), а не клінічно відкалібровані значення. Алгоритм прозорий, ваги змінюються в одному місці (`RISK_WEIGHTS`).
- **Чи це медичний засіб?** Ні, у застосунку й у звіті це прямо зазначено.
- **Чому SQLite, а не лише хмара?** Local-first: застосунок швидкий і працює без інтернету, а хмара (Supabase) потрібна тільки для синхронізації між пристроями. Аналіз індексу виконується локально.
- **Де зберігаються дані і хто їх бачить?** Локально в SQLite і в Supabase Postgres; завдяки Row Level Security кожен бачить лише свої записи. Нотатки не шифруються на сервері — це обмеження.
- **Чому Expo?** Один код для iOS, Android і веба; швидка перевірка в Expo Go.
- **Чим точний прогноз?** Це проста лінійна екстраполяція останніх 10 днів, груба оцінка (так і підписано в інтерфейсі).

## Обмеження (чесно)

- Тестувалося в браузері та через збірку бандлів; на фізичному телефоні в Expo Go перевіряти треба окремо (особливо сповіщення, біометрію та вікно «Поділитися»).
- Словник сентименту невеликий і не розуміє контексту чи сарказму.
- Сповіщення в Expo Go на Android обмежені; повноцінно перевіряються на iOS або у власній збірці.
- Якщо один і той самий день відредагувати на двох пристроях між синхронізаціями, виграє пізніше збереження, а раніша зміна втрачається.
- Перший вхід і реєстрація потребують інтернету; підтвердження email залежить від налаштувань Supabase.
- Сповіщення в браузері приходять лише при відкритій вкладці й показуються від імені браузера (так працює macOS/Chrome); іконка застосунку в сповіщенні з'являється лише в окремій збірці, не в Expo Go.
